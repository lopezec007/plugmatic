# Deviations from the implementation spec

| Date (UTC) | Spec ref | Deviation | Rationale | Architectural? |
|---|---|---|---|---|
| 2026-08-02 | Appendix / §6.5 | Programming cable is **CH340 (1A86:7523)**, not FTDI. FTDI kept as secondary candidate ID. | lsusb on the actual cable | no |
| 2026-08-02 | §4.2 | `IRadioCodec.Encode` gained an optional `baseImage` parameter: `Encode(Codeplug ir, ReadOnlyMemory<byte>? baseImage = null)`. Hardware writes encode on top of the same-run `pre-write.bin` so settings/unknown blocks are carried forward; `build` runs encode from scratch. | The DM-32UV image contains opaque per-radio blocks (calibration-adjacent settings) that must survive a write; D7 guarantees a base image is always available on the hardware path. | no (additive) |
| 2026-08-02 | §3.2 | In addition to qdmr, the MIT-licensed community spec github.com/infamy/DM32-Protocol-Spec is used as a primary documentation source (it is the second source for cross-validation; its CPS capture file is vendored as a fixture). | Two-source rule satisfied without hardware risk | no |
| 2026-08-02 | §6.3 (addition) | New invariant (user-directed at ladder step 6): **DMR TX requires a configured operator DMR ID** (`config set dmr.id`). Builder forces all DMR channels RX-only without it; validator rejects TX-enabled DMR channels when `Settings.RadioId == 0`; codec never touches the radio-ID block when the IR carries no ID. | Radio transmitted with a zeroed ID during testing — unidentified DMR TX must be impossible | no (additive safety) |
| 2026-08-02 | §7.5 / ladder | Ladder steps 5–6 completed; per user request the generated Fort Collins plug REMAINS on the radio (original archived as the `factory-golden` read run and in every write run's `pre-write.bin`). | User preference | no |
| 2026-08-10 | §6.4 / format §1 | **Image window widened to the full 0x100000 virtual block space.** The old [0x03000,0x68000) window silently skipped 11 of this radio's 107 mapped blocks, so reads — including `pre-write.bin` backups — were incomplete and those blocks were never written. Protocol now refuses a read whose mapped blocks fall outside the window; legacy-sized images are still accepted (0xFF-padded) so old backups stay restorable. | A backup that skips blocks is not a backup | no (strictly safer) |
| 2026-08-10 | §3.2 / format §4 | **qdmr fact corrected by hardware:** the channel scan-list field is a *literal* 1-based index in bits 6–0 of 0x19, not a nibble at bits 5–2. The shifted encoding made the radio use list index×4. Proven by having the radio itself rewrite three channels (0x01, 0x01, 0x89). The user's pre-plugmatic codeplug carries the same ×4 pattern, so whatever wrote it shared the bug — that image is not evidence. | Two-source rule: hardware outranks both references | no |
| 2026-08-10 | §6.3 (addition) | Radio-wide call-match flags (settings block 0x04, +0x060, bits 0–1) are now authored by plugmatic, written **off** (the radio's shipped default) at the user's request. Read-modify-write of two bits only; the block is never fabricated when absent. | User request; previously pure passthrough | no |
| 2026-08-10 | Spec §1/§10 (scope) | **Second radio added: AnyTone AT-D878UVII+** (`--radio d878uv`), at the user's direction. The v3 spec scopes v1 to the DM-32UV and lists other radios as out of scope, so this is v2 work. Introduced `IRadioDefinition` + `RadioRegistry`; every command is now radio-agnostic. Same disciplines apply unchanged: facts→docs→code, two-source cross-validation, read-only probing first, ladder before writes. | User request | yes — approved by the user |
| 2026-08-10 | d878uv | AnyTone support is **read/backup only** (`SupportsWrite = false`): identify, full read, decode of channels/zones/contacts/radio-ID. `write` refuses for this radio until the format doc is complete and hardware-verified. | Nothing gets written from unverified facts | no |
| 2026-08-10 | §6.3.1 / §5.1 | `RawRecord`/`RawBlocks` are now `[YamlIgnore]`. They are binary fidelity state, not part of the human-facing IR, and were making `read.yaml` mostly byte arrays (1536 of 2741 lines on the D878). Consequence: `write --plug read.yaml` rebuilds records from modeled fields instead of preserving unmodeled bits — byte-exact restore is `write --image <run>/pre-write.bin`, which is the documented recovery path anyway. | read.yaml is specified as the reviewable decoded IR | no |
| 2026-08-10 | d878uv / ladder step 4 | **AnyTone write support blocked by hardware behaviour.** Correctly framed 16-byte writes are ACKed and silently not applied (proven on both unallocated and allocated records, across session close/reopen). Both references write exactly this frame with no prepare/commit step, so either the V101 firmware needs something neither implements, or their AnyTone write paths are stale. `SupportsWrite` stays false; unblocking needs a USB capture of the official CPS writing. | Nothing is written from a protocol we cannot demonstrate works | no |
| 2026-08-10 | §3.5 step 4 (ladder) | **A no-op writeback is not sufficient evidence that a write path works.** Writing identical bytes back passes trivially when the radio ignores writes entirely. Ladder step 4 now requires a *mutation* test: change a byte, read it back, then restore. Added as `plugmatic dev writetest --prove`. | The identical-write test returned a false PASS on the AnyTone | no (strictly stronger) |
| 2026-08-20 | d878uv / ladder step 4 | **The 2026-08-10 "writes are ACKed and not applied" finding was wrong.** The CPS capture showed identical framing to ours, and hardware then showed why our probe failed: writes are *staged* and commit on `END`, and **any read after a write discards everything staged**. Our probe read its target back in the same session, which both returned pre-write bytes and destroyed the write it was checking. Its one cross-session test used addresses (`0x00841200`, `0x00FC07C0`) that are not backed by storage, so the only experiment that could have caught this landed on the only class of address that cannot answer. | Hardware outranks our own earlier conclusions too | no (correction) |
| 2026-08-20 | §3.5 step 4 (ladder) | **A mutation test must read back in a *separate session* on this radio**, or it reports a false negative exactly as loudly as a no-op writeback reports a false positive. `dev writetest` rewritten accordingly. | The 2026-08-10 lesson was right in kind and wrong in detail | no (strictly stronger) |
| 2026-08-20 | d878uv / format §2 | **A write erases the aligned 0x40000 (256 KB) block around it** and keeps only what the session staged. The region table describes 1.63 MB scattered across blocks holding far more (the block at `0x00800000` is covered for 0x2000 of 0x40000, while the CPS keeps channel data at `0x00802000-0x00804000`), so any write would wipe codeplug bytes we have never read. `SupportsWrite` stays **false**; `BuildWritePlan` refuses under-covered blocks by address instead of writing them. Unblocking = read whole erase blocks raw and rewrite them complete (preferred), or extend the region table. | A write path that destroys unmodelled data is worse than no write path | no |
| 2026-08-20 | §3.5 step 4 (ladder) | **New ladder rule: establish the erase granularity before the first write, and check for damage across that whole granularity — not across the bytes written.** Learned by destroying channel banks 0 and 1 with two 16-byte probes that both *passed*, because each only re-read its own 16 bytes. Blast radius was 16,384× the verified region. Data recovered byte-exactly from the CPS capture. `dev writetest` now works only in a block it has confirmed holds no codeplug data. | A probe that cannot see its own crater is not a safety test | no (strictly stronger) |
| 2026-08-20 | d878uv / format §2 | Firmware keeps a 16-byte signature (`FF FF FF FF 22 33 44 55 FF FF FF FF 55 55 AA AA`) at the end of every 0x20000 half-block. It is firmware-managed — present in never-written blocks and restored after an erase — so emptiness checks must ignore it (`Layout.IsFlashMarker`). | Otherwise every block looks "in use" | no |
| 2026-08-20 | §4.2 | `IRadioProtocol.WriteImageAsync` gained a `baseline` parameter (the image just read from the radio) and `IRadioDefinition` gained `SeparateReadWriteSessions`. The AnyTone needs read, write and verify in three distinct sessions; the DM-32UV path is unchanged (`false`, default interface implementation). | The write flow cannot verify in the session that wrote | no (additive) |
