# Deviations from the implementation spec

| Date (UTC) | Spec ref | Deviation | Rationale | Architectural? |
|---|---|---|---|---|
| 2026-08-02 | Appendix / §6.5 | Programming cable is **CH340 (1A86:7523)**, not FTDI. FTDI kept as secondary candidate ID. | lsusb on the actual cable | no |
| 2026-08-02 | §4.2 | `IRadioCodec.Encode` gained an optional `baseImage` parameter: `Encode(Codeplug ir, ReadOnlyMemory<byte>? baseImage = null)`. Hardware writes encode on top of the same-run `pre-write.bin` so settings/unknown blocks are carried forward; `build` runs encode from scratch. | The DM-32UV image contains opaque per-radio blocks (calibration-adjacent settings) that must survive a write; D7 guarantees a base image is always available on the hardware path. | no (additive) |
| 2026-08-02 | §3.2 | In addition to qdmr, the MIT-licensed community spec github.com/infamy/DM32-Protocol-Spec is used as a primary documentation source (it is the second source for cross-validation; its CPS capture file is vendored as a fixture). | Two-source rule satisfied without hardware risk | no |
| 2026-08-02 | §6.3 (addition) | New invariant (user-directed at ladder step 6): **DMR TX requires a configured operator DMR ID** (`config set dmr.id`). Builder forces all DMR channels RX-only without it; validator rejects TX-enabled DMR channels when `Settings.RadioId == 0`; codec never touches the radio-ID block when the IR carries no ID. | Radio transmitted with a zeroed ID during testing — unidentified DMR TX must be impossible | no (additive safety) |
| 2026-08-02 | §7.5 / ladder | Ladder steps 5–6 completed; per user request the generated Fort Collins plug REMAINS on the radio (original archived as the `factory-golden` read run and in every write run's `pre-write.bin`). | User preference | no |
| 2026-08-10 | §6.4 / format §1 | **Image window widened to the full 0x100000 virtual block space.** The old [0x03000,0x68000) window silently skipped 11 of this radio's 107 mapped blocks, so reads — including `pre-write.bin` backups — were incomplete and those blocks were never written. Protocol now refuses a read whose mapped blocks fall outside the window; legacy-sized images are still accepted (0xFF-padded) so old backups stay restorable. | A backup that skips blocks is not a backup | no (strictly safer) |
| 2026-08-10 | §3.2 / format §4 | **qdmr fact corrected by hardware:** the channel scan-list field is a *literal* 1-based index in bits 6–0 of 0x19, not a nibble at bits 5–2. The shifted encoding made the radio use list index×4. Proven by having the radio itself rewrite three channels (0x01, 0x01, 0x89). The user's pre-plugmatic codeplug carries the same ×4 pattern, so whatever wrote it shared the bug — that image is not evidence. | Two-source rule: hardware outranks both references | no |
| 2026-08-10 | §6.3 (addition) | Radio-wide call-match flags (settings block 0x04, +0x060, bits 0–1) are now authored by plugmatic, written **off** (the radio's shipped default) at the user's request. Read-modify-write of two bits only; the block is never fabricated when absent. | User request; previously pure passthrough | no |
| 2026-08-10 | Spec §1/§10 (scope) | **Second radio added: AnyTone AT-D878UVII+** (`--radio d878uv`), at the user's direction. The v3 spec scopes v1 to the DM-32UV and lists other radios as out of scope, so this is v2 work. Introduced `IRadioDefinition` + `RadioRegistry`; every command is now radio-agnostic. Same disciplines apply unchanged: facts→docs→code, two-source cross-validation, read-only probing first, ladder before writes. | User request | yes — approved by the user |
| 2026-08-10 | d878uv | AnyTone support is **read/backup only** (`SupportsWrite = false`): identify, full read, decode of channels/zones/contacts/radio-ID. `write` refuses for this radio until the format doc is complete and hardware-verified. | Nothing gets written from unverified facts | no |
